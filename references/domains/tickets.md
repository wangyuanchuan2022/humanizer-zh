# 领域 — 工单与工作任务

覆盖 issue 工单、任务、工作指令（work order）、你提交的 bug 报告（不是回复——那是 `dev-replies.md` 的事）。与 `professional-pass.md` 配合运行（短答复加权）。

## 人类基线

祈使、极简、够用即可。接手人应该不用问问题就能开工，并且知道什么时候算完。跟踪器的字段模板是容器，不是破绽。

## 本领域的 AI 特征

| 特征 | 修法 |
|---|---|
| 在诉求之前写小说长度的背景 | 背景只写接手人不知道的部分；其余给链接 |
| 描述用句子把标题复述一遍 | 描述从标题停下的地方开始 |
| 枚举显而易见的步骤（「1. 打开仓库。2. 找到文件…」） | 只写不显然的步骤和确切命令 |
| 含糊验收："works correctly"、"improved performance" | 可测判据：跑哪条命令、什么输出算完（"p95 < 200ms on the staging load test"） |
| 每个模板字段都为凑齐填上散文 | 空是合法值；「N/A」胜过一段空话 |
| 圆整的范围词："refactor the module"、"clean up" | 具体边界：哪些文件/函数算在内，哪些明确排除 |
| 中文示例行（安置自 v4.6 §30）：描述只写旧版本的行为而不写现状 | 文档只写当前行为（见规则 6） |

## 规则

1. **标题 = 结果**，不是动作（「重试队列在重新部署时丢任务」，不是「调查队列问题」）。
2. Bug 工单：确切复现（版本、命令、输入）、预期 vs 实际（贴真实输出）、频率。复现不了，就写你试过什么。
3. 验收判据可测，否则就不是判据。
4. 链接，不重复：先前的工单、设计文档、告警。事实只有一个源头。
5. 优先级/估时诚实且裸——不配论证段落。
6. **只写当前行为，不描述旧版本**（安置自 v4.6 §30）：工单描述当前（现状/预期）行为；旧行为只在「预期 vs 实际」复现对照里以真实输出出现。
