# 领域 — 技术文章与博客

覆盖工程博客、教程、架构综述、经验报告。最丰富的领域：与 `professional-pass.md` 配合运行（文章型加权），跑 `discourse-pass.md` §1–3 的大纲/QUD 检查，以及 `style-pass.md`（跳过其虚构腔表）。

## 人类基线

由作者真实碰到的真问题驱动。设计上就不均匀——有意思的地方深，没意思的地方一行。至少有一条死胡同，至少一个读者可以不同意的主张，数字带着条件。第一人称与缩略（contractions）正常。

## 本领域的 AI 特征

| 特征 | 修法 |
|---|---|
| 主题综述式开场："In the world of distributed systems…"／解释每个读者早已知道的定义 | 从事故、bug、让你抬头看的那个数字开场 |
| 风衣裹着的清单（listicle in a trench coat）：表面是散文，骨子里是「The first… The second… The third…」 | 或者诚实的结构（真列表/真表格），或者有论证的真散文 |
| 分形摘要（fractal summary）：每节预告、正文、复述 | 说一次，在它所属的层级 |
| 发明概念标签：文中自造「the observability paradox」「configuration drift syndrome」 | 平实描述，或用已确立的术语 |
| 对称覆盖：每个备选一段，没有一个给裁定 | 承诺一个推荐，并给出会让你改主意的那个条件 |
| 全程无失败：每步都成功、基准印证论点 | 写进什么坏了、先试了什么、下次会跳过什么——模型系统性省略死胡同，而那恰是读者信任的部分 |
| 从未运行过的泛化代码示例（`foo`、`my_service`） | 来自实际工作的真实、可运行、测过的片段——或者明说是草图 |
| 无条件的基准（benchmark） | 机器、版本、数据集大小、跑几次——或者别印那个数字 |
| 两边讨好式结论 + 未来展望 | 停在推荐上，或你真实拥有的开放问题上 |

## 规则

1. **问题先于主题。** 第一段：迫使你提出问题的具体情境。没有真实情境，诚实的体裁是「X 笔记」，不是亲历记——绝不编造事故（SKILL.md「不编造细节」硬护栏）。
2. 至少一个主张，以你的名义说出，带不同意条件（「如果你的写入低于 1k/s，以下全部不用看」）。
3. 深度预算按兴趣分配，不按对称：让你吃惊的那节拿到的字数，是准备步骤的 5 倍。
4. 数字带条件；主张带链接；代码带「跑过」保证或免责声明。
5. QUD 检查：如果小节-问题序列读起来是「X 是什么 → X 为何重要 → 怎么做 X → 结论」，围绕实际发生的事重组。
6. 声音：第一人称、缩略、一两处旁白。实测过的人类标记（立场、不均匀、亲历细节）与专家读者判断「这是个人写的」用的是同一批。
