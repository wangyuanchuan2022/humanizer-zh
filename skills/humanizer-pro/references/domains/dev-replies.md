# 领域 — PR 回复、Issue 回复、评审评论

覆盖 pull request 与 issue 上的回复、代码评审评论、讨论串回应。与 `professional-pass.md` 配合运行（短答复加权：事实性、具体性、模板化）。

## 人类基线

直接、具体、成比例。维护者第一句就答到点上，引用确切的代码或报错，直率地不同意，在属实时说「我不知道」或「不予修复」。简短是常态，不是无礼。**先读讨论串和维护者的其他回复——对齐那个语域**，而不是某种通用礼貌标准。没有讨论串可抽样时，适用本基线。

## 本领域的 AI 特征

| 特征 | 修法 |
|---|---|
| 缺省的称赞/感谢开场："Great catch!"、"Thanks for the detailed report!" | 开门见山给答案。真正值得感谢时才谢（首次贡献、异常用心）——不作为条件反射 |
| 回答前把问题/issue 复述一遍 | 删；讨论串里已经有了 |
| 一句话能答的写成一堵项目符号墙 | 一句话。篇幅与利害成正比 |
| 含糊不答："There could be several factors…"、两面讨好 | 表态：最可能的原因、确认它的检查，或诚实的「我不知道」 |
| 对 bug 报告的模板化共情："I understand how frustrating this must be" | 去要你真正需要的复现细节 |
| 落款客套："Hope this helps!"、"Let me know if you have any questions!" | 内容到哪结束就到哪结束 |
| 在回复里许诺而不是动手（"I'll look into this"）而修复近在眼前 | 做掉，然后贴 commit |
| 一场评审里评论结构完美统一（每条评论：称赞+问题+建议） | 有变化；有的评论一个词（"nit: typo"），有的是整段 |
| 中文示例行（安置自 v4.6 §20-22）：「希望这对你有帮助！」「这是个好问题！」「你说得非常对！」「当然可以！」「以下是…」等客服式残留、讨好开场与知识截止免责（「截至我所掌握的信息」「据悉」） | 全部删除，直接回应；免责改为说明来源里没有什么或删句 |

## 规则

1. **答案先行。** 第一句给裁定/答案；理由在后，按需给。
2. 引工件（artifact）：`file.py:214`、commit SHA、逐字的报错文本、文档链接。关于代码的主张指向代码。
3. 直率地不同意并给理由（"This breaks the retry path — see #388"）——不裹道歉、不搞称赞三明治。
4. 诚实且廉价地表态不确定：「不确定——2.4 上能复现吗？」胜过三段含糊。
5. 不修/超出范围（wontfix/out-of-scope）：直说，给一条理由，链接当初定论的政策或 issue。不要软化成让报告者自己去解码的含糊。
6. 评审评论里显式区分严重度（blocking vs nit），按仓库既有做法。
